# Aurora Elo — trabalho com Hermes

Este é o checkout Git do Aurora Elo. Confirme a branch com `git status` antes de
editar; não troque de branch, faça commit, push ou deploy sem pedido explícito.
Não confunda este checkout com o diretório histórico `mindcare` ou a VPS.

## Referência visual

- Use exclusivamente `design_system/` como referência visual da nova versão.
- Não considerar `design_system_duralux/`: não recuperar/copiar esse pacote nem
  exigir sua presença para testes ou aceite. Preserve as evidências históricas.
- `static/duralux/` é uma dependência de runtime legada distinta; mantenha somente
  o necessário à compatibilidade e valide assets/CSP/URLs enquanto integra o
  design system escolhido. Não apagar dependências ativas indiscriminadamente.

## Divisão de trabalho

- Configuração e justificativa: `docs/migration/hermes-model-routing.md`.
- Principal: arquitetura, implementação integrada, autorização, isolamento entre
  clínicas, consentimento, prontuário, migrations e aprovação final.
- Auxiliares: tarefas delimitadas por domínio/arquivo, testes com dados sintéticos,
  tipagem, componentes isolados e documentação. Evite escrita concorrente no mesmo
  arquivo, sobretudo em settings, rotas, migrations e shell visual.
- Exija revisão independente de mudanças clínicas ou de segurança; `/review` usa
  o modelo de revisão configurado no perfil. Delegação comum não seleciona um
  modelo por especialidade automaticamente.
- Exija dos auxiliares arquivos alterados, comandos executados, resultados e
  limitações. Confirme os resultados antes de declarar conclusão.

## Segurança e validação

- Não leia `.env`, credenciais, bancos, uploads ou prontuários reais. Não envie
  dados clínicos a provedores de desenvolvimento. Use dados sintéticos.
- Não altere o provedor de IA do produto ao configurar modelos do Hermes.
- Preserve `accounts.User`, migrations existentes e contratos entre domínios.
- Revise especialmente `psychiatry/`: não presuma que o tenant middleware protege
  todas as APIs nem que a suíte histórica cobre esse domínio.
- Nunca descreva simulações de persistência, SOS ou notificação como operação real.
- Use o settings de teste e os comandos documentados no README para pytest, Ruff e
  mypy. Compare falhas com um baseline atual; não enfraqueça testes para ocultá-las.
- Mudanças de UI exigem i18n e validação renderizada; mudanças mobile exigem
  verificação própria, sem tratar `expo start` como build/teste aprovado.
- Responda em português. Diferencie evidência estática, execução local e produção.
